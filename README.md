# wellprod — production analytics over Argentina's open well data

Working analytics over the **official per-well oil & gas production dataset** published by the
Secretaría de Energía de la Nación. Ingests a full year, reports on its quality, and profiles
production by basin, operator, formation and resource type.

## English

### Results on the real 2026 file

The complete published file: **653,543 well-month records**, 212 MB, sha256 recorded in the
manifest. Reproduce it with three commands (below).

**The file is mostly not production.** 463,557 of 653,543 records — **71%** — report zero oil
*and* zero gas. Only **29.07%** of the file is eligible for modelling. An analysis that skips this
step models noise with confidence.

| Check | Value |
| :--- | ---: |
| Rows | 653,543 |
| Missing contract columns | **0** |
| Rows with zero oil **and** zero gas | 463,557 (71%) |
| Rows in placeholder fields (`SIN NOMBRE`, …) | 3,728 |
| Rows with administrative province (`Estado Nacional`) | 512 |
| Rows with an implausible gas-oil ratio | 55,009 |
| **Modeling-eligible share** | **29.07%** |

**Conventional and unconventional are two different businesses**, and the numbers say so:

| Resource type | Wells | Oil (m³) | Share of national oil | Water cut |
| :--- | ---: | ---: | ---: | ---: |
| NO CONVENCIONAL | 5,102 | 24,202,834 | **69.5%** | 42.3% |
| CONVENCIONAL | 77,908 | 10,603,064 | 30.5% | 78.2% |

Six per cent of the wells produce seventy per cent of the oil, at roughly half the water cut.

By basin, Neuquina holds **78.2%** of national oil across 32,619 wells, while Austral shows a
median gas-oil ratio of **11,419 m³/m³** — a gas-prone basin, exactly as its geology implies. By
operator, YPF accounts for 41.0% of oil and Vista Energy produces 8.7% of the national total from
489 wells, with the lowest water cut in the top five at **23.5%**.

Every number above comes from `reports/`, which is generated by the tool and committed, with the
source file, its row count and its hash attached.

### The problem this starts with

In this dataset the gas column is labelled `prod_gas` and documented as **`Mm3`**. The published
values are **miles de metros cúbicos** — *thousands* of cubic metres, not millions.

Treat that as millions and every gas-oil ratio you compute is **1000× too large**. The resulting
number is 98,700 instead of 98.7 m³/m³, and 98,700 still looks like something a person might
believe. Nothing crashes. No warning is raised. The analysis is simply wrong.

So the unit of every column is declared **once**, in `wellprod.schema`, attached to the column that
carries it. `gas_oil_ratio()` is the only sanctioned way to compute a ratio, and a regression test
pins the factor:

```python
def test_gas_oil_ratio_uses_thousands_not_millions():
    ratio = series_ratio([5.0], [100.0]).iloc[0]

    assert GAS_M3_PER_UNIT == 1_000.0
    assert ratio == pytest.approx(50.0)  # not 50 000
```

That test exists because I made this exact mistake in a previous project. The data there was under
an operator's confidentiality, so the correction could not be published. This is the public
version, on public data, where anyone can check the arithmetic.

### Install and run

```bash
git clone https://github.com/Lucas-Arteaga/well-production-analytics.git
cd well-production-analytics
uv sync

# download and cache a full year as Parquet (about 30 seconds; 212 MB)
uv run wellprod ingest --year 2026

# quality report, and a profile per dimension
uv run wellprod report --year 2026 --out reports --top 15

# or one dimension at a time
uv run wellprod profile --year 2026 --by empresa --top 10
```

There are no data files in the repository and none in CI. The tests build their own frames from the
contract, so the suite runs in about three seconds with no network.

### What is in the box

| Module | What it does |
| :--- | :--- |
| `wellprod.schema` | The column contract: all 38 published columns with their unit and conversion factor, the business-valid value sets, `gas_oil_ratio()` and a plausibility band |
| `wellprod.ingest` | Resolves the official CSV through the CKAN API, downloads it, reads it in chunks and caches it as Parquet with a manifest (row count, sha256, truncation) |
| `wellprod.quality` | `build_report()`: nulls, duplicates, negative volumes, rows with no oil or gas, placeholder fields, administrative provinces, implausible ratios, and the share eligible for modelling |
| `wellprod.profile` | `profile_by()`: production by any of nine dimensions, in cubic metres, with a median gas-oil ratio and a water cut that is `NaN` rather than zero when there is no liquid |
| `wellprod.cli` | `ingest`, `quality`, `profile`, `report` |

### Design decisions worth stating

1. **Units live with the column, never inline.** A conversion factor hardcoded anywhere but
   `schema.py` is a bug, not an optimisation.
2. **The download URL is resolved at run time, not hardcoded.** The dataset publishes per-resource
   UUIDs that change when the Secretaría re-uploads a file. Hardcoding one means the project
   silently breaks later.
3. **The ratio function refuses to invent a number.** If oil production is zero the ratio is `NaN`,
   not infinity and not zero. A ratio from a well that is not producing is noise, and filtering
   belongs upstream where the analyst can see it happen.
4. **The median gas-oil ratio, not the mean.** A handful of gas wells sit four orders of magnitude
   above the rest. A mean would describe those wells and call it a basin.
5. **Truncation is recorded, not hidden.** `--limit` produces a biased head of the file — it is
   ordered by operator code — so the manifest records the truncation and every report states it.
6. **Every report carries its provenance.** Source name, row count and sha256. A report without
   provenance is a claim.
7. **No data files in CI.** The tests build frames from the contract, so the suite is fast and the
   logic is proven without a 200 MB download.

### El problema con el que arranca

En este dataset la columna de gas se llama `prod_gas` y está documentada como **`Mm3`**. Los valores
publicados son **miles de metros cúbicos**, no millones.

Si los tratás como millones, **toda relación gas-petróleo que calcules queda 1000× más grande**. Da
98.700 en lugar de 98,7 m³/m³, y 98.700 sigue pareciendo un número creíble. No falla nada, no salta
ninguna advertencia: el análisis simplemente está mal.

Por eso la unidad de cada columna se declara **una sola vez**, en `wellprod.schema`, pegada a la
columna que la lleva. `gas_oil_ratio()` es la única forma habilitada de calcular una relación, y un
test de regresión fija el factor en 1.000.

Ese test existe porque **cometí exactamente este error** en un trabajo anterior. Los datos de ese
trabajo estaban bajo confidencialidad de una operadora, así que la corrección no se pudo publicar.
Esta es la versión pública, sobre datos públicos, donde cualquiera verifica la aritmética.

### Instalar y correr

```bash
git clone https://github.com/Lucas-Arteaga/well-production-analytics.git
cd well-production-analytics
uv sync

uv run wellprod ingest --year 2026          # descarga y cachea el año (~30 s, 212 MB)
uv run wellprod report --year 2026 --out reports --top 15
uv run wellprod profile --year 2026 --by empresa --top 10
```

partir del contrato, así que la suite corre en unos tres segundos sin red.

### Decisiones de diseño que vale la pena declarar

1. **Las unidades viven con la columna, nunca sueltas en el código.** Un factor de conversión
   escrito en cualquier lugar que no sea `schema.py` es un bug, no una optimización.
2. **La URL de descarga se resuelve en tiempo de ejecución, no se hardcodea.** El dataset publica
   UUIDs por recurso que cambian cuando la Secretaría re-sube un archivo.
3. **La función de la relación se niega a inventar un número.** Si el petróleo es cero, la relación
   es `NaN`. Una relación de un pozo que no produce es ruido.
4. **La mediana de la relación gas-petróleo, no el promedio.** Un puñado de pozos gasíferos está
   cuatro órdenes de magnitud arriba del resto.
5. **El truncado se registra, no se esconde.** `--limit` produce una cabeza sesgada del archivo
   (está ordenado por código de operadora), así que el manifiesto lo registra.
6. **Todo reporte lleva su procedencia.** Nombre del archivo, filas y sha256.
7. **Sin archivos de datos en CI.**
